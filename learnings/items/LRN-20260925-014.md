# DBX 插件 NAS 联调链与同版本覆盖风险

### Summary
NAS 本机联调走「`POST /api/auth/login {password}` 拿 cookie → `POST /api/plugins/install?allow_unsigned=true` 传 dev 包 → `POST /api/plugins/invoke {pluginId,method,params,timeoutMs}` 直调 → `connection/connect` 自建会话再验业务 RPC」；**同版本号覆盖安装会把生产激活版本切过去**，验完必须装回原包，`uninstall` 在有连接绑定时拒绝，可做恢复手段但别指望。

### Details
- 登录：`curl -c jar POST /api/auth/login -d '{"password":"$PW"}'`（`$PW` 现查 `dbx.env`，不落盘），后续请求带 `-b jar`。
- 安装：multipart `-F file=@x.dbxp`；`connection-action` 只认内置库类型，插件连接会话用 `invoke connection/connect` 自建（如 `{"connection":{"id":"verify-conn","log_dir":"/app/data"}}`）。
- 本轮实测：`logs/browse` 根/下钻、`logs/search` 相对路径、`../` 拦截全通；但 dev 包（同为 0.1.0）覆盖了生产激活版本，恢复时正式 0.1.0 包又因 musl 起不来（见 [[TD-20260925-004]]），最终用 `dist` 的 beta.2 gnu 包重装才切回可用版。
- 教训：联调包版本号加 `-dev` 后缀也救不了（DBX 按 id 覆盖落盘），生产有连接绑定时**先确认当前激活版本能回滚**再覆盖。

### Suggested Action
联调前先 `file` 确认落盘 bin 的 interpreter，并备好可用的旧版包；验完立即装回。发版修好前勿动生产插件。
